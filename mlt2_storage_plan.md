## Мінімальна предметна модель

- `analysis_run`: ідентифікатор запуску, час, параметри фільтра/пошуку піків, стан виконання.
- `file_result`: FK на запуск, `source_id`, назва/посилання на файл, sample rate Hz, кількість каналів/кадрів для успішного результату; статус і код/повідомлення для помилки. Читання може не дати метаданих — не вигадувати їх для error row.
- `spectral_peak`: FK на результат файла, індекс каналу, частота Hz, амплітуда; нуль рядків для помилки або сигналу без піків.

Nullable/check правила success/error, `UNIQUE(run_id,source_id)` і managed NPZ реалізовані в schema/store. При повторному аналізі того самого WAV створюється результат іншого запуску. Масиви не розкладаються на SQL rows/JSON. Storage API приймає готовий JobResult і перевіряється без UI; lifecycle/backup/orphan обмеження наведені в `system.md`.

## SQLite чи серверна СУБД

**Для першої локальної версії — SQLite, відповідно до доручення почати рекомендований план 2026-11-24.** Припущення: один backend на одному хості; DB writes централізовані в одному головному процесі, транзакції короткі. SQLite є SQL СУБД з дисковим файлом без окремого сервера; Python має стандартний `sqlite3`. У кожному connection потрібно явно вмикати й перевіряти FK enforcement (`PRAGMA foreign_keys=ON`).

Майбутній web frontend працює з backend API, а файл SQLite залишається локальним для backend. Сам факт вебінтерфейсу не вимагає серверної БД. При багатьох незалежних writers, кількох backend-хостах зі спільною БД або вимозі SQL stored procedures розглядати PostgreSQL/MySQL. Перенесення між СУБД не вважати безкоштовним: окремий storage API локалізує зміни, але DDL/SQL/міграції й перевірки потрібно адаптувати.

Офіційні джерела, перевірені 2026-11-23:

- [Застосування SQLite](https://www.sqlite.org/whentouse.html): локальне сховище, можливе використання для web backend, один одночасний writer, критерії client/server engine.
- [Python 3.13 sqlite3](https://docs.python.org/3.13/library/sqlite3.html): вбудований DB-API, без окремого server process; `Connection.create_function` реєструє функцію для connection.
- [SQLite foreign keys](https://www.sqlite.org/foreignkeys.html), [CREATE TRIGGER](https://www.sqlite.org/lang_createtrigger.html): реальні FK/triggers та правила їх застосування.
- [SQLite SQL syntax](https://www.sqlite.org/lang.html) і [SQLite forum: stored procedures](https://sqlite.org/forum/info/b7ea1c20fae4cc5d): у стандартного SQLite немає звичайних SQL stored procedures; application-defined function не є збереженою процедурою і потребує реєстрації у connection.

## Невирішений нюанс навчального завдання

Завдання перелічує таблиці, поля, тригери, функції, збережені процедури тощо. Реалізований за погодженим планом SQLite дозволяє тестувати таблиці/FK/checks/triggers і SQL functions, але не стандартний `CREATE PROCEDURE/CALL`. Чи вимагає викладач саме окремої процедури — не встановлено. Якщо так, цей пункт потребуватиме MySQL/PostgreSQL; Python-функція не є заміною процедури. Поточний протокол явно описує межі SQLite та не заявляє непідтримуваного тестування.

Усі перелічені напрями перевірені у фінальному наборі: DB9 tests (seed/SQL functions, constraints/FK/cascade, triggers, run lifecycle, rollback/NPZ cleanup, reopen/arrays, history/schema version) плюс окремі worker/pool/scheduling/aggregation/crash/CLI checks. Фактичні команди й результати — `testing.md`; вихідний план не є самостійним доказом проходження.
