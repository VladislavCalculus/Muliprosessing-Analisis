# План MLT-2 і сховища результатів

Дата: 2026-11-23. Статус: пропозиція за запитом користувача, лише планування. Реалізація БД раніше призупинена; запит скласти план не відновлює її автоматично. MLT-3 буде вебінтерфейсом і реалізовуватиметься останнім (D-12). Jira scope зіставлено з live snapshot у `jira.md`, нових Jira issues/status changes не робили.

## П'ять невеликих етапів

| Етап | Робота | Конкретний результат |
| --- | --- | --- |
| 1. Один worker і контракти | Визначити легкий file job, конфігурації та корельований outcome; виконати наявні `audio_io → signal_proc` для одного файла. Орієнтир MLT-21. | Успіх або помилка зі стабільним `source_id`; DSP/reader API не переписуються. |
| 2. Паралельний batch | Пул із явно заданою/обмеженою кількістю процесів, розподіл файлів, збір статусів і коректне завершення. Орієнтири MLT-19/22/29. | Кілька WAV обробляються паралельно; звичайна помилка файла відокремлена від аварії worker-процесу. Для останньої окремо реалізувати ізоляцію/відновлення решти задач без нескінченних повторів. Не оголошувати MLT-29 виконаним тільки через додавання пулу. |
| 3. Окреме сховище | `src/result_store/` зі schema SQL та невеликим Python API: створити запуск, записати результат/помилку, прочитати історію. | Ланцюжок `analysis_run 1:N file_result 1:N spectral_peak`, незалежний від UI й керування процесами. |
| 4. З'єднати pipeline і БД | Головний процес записує результати після збору MLT-20; один результат і всі його піки — одна транзакція. Додати CLI запуску й перегляду історії. | Робочий batch до появи вебки; помилки збереження видимі викликачеві. Workers не мають DB connections і не використовують БД замість IPC. |
| 5. Перевірки та протокол ПЗ | Виконати компактні перевірки реальної БД й pipeline; додати мінімальні seed-дані та повні SQL/test listings у протокол. | Фактичні результати, а не заплановані проходження; орієнтир 8–10 змістовних DB cases, без вимоги штучно вкласти всі види перевірок у цей ліміт. Формат — за `~/kpi3/kpi4/arh/`. |

Зв'язки з Jira є орієнтирами інтеграції, не дозволом змінювати її склад/AC. Збереження історії — запропоноване розширення, відсутнє в поточних descriptions/AC.

## Мінімальна предметна модель

- `analysis_run`: ідентифікатор запуску, час, параметри фільтра/пошуку піків, стан виконання.
- `file_result`: FK на запуск, `source_id`, назва/посилання на файл, sample rate Hz, кількість каналів/кадрів для успішного результату; статус і код/повідомлення для помилки. Читання може не дати метаданих — не вигадувати їх для error row.
- `spectral_peak`: FK на результат файла, індекс каналу, частота Hz, амплітуда; нуль рядків для помилки або сигналу без піків.

До затвердження DDL потрібно визначити точні nullable/check правила для success/error, кореляцію `UNIQUE(run_id, source_id)` і життєвий цикл артефактів. При повторному аналізі того самого WAV створюється результат іншого запуску. Для великих масивів/спектрів рекомендуються окремі файли з посиланнями, без автоматичного перетворення ndarray на SQL rows чи JSON. Початковий storage API може приймати вже готовий DSP outcome — етап 3 можна перевірити без завершеного пулу та UI.

## SQLite чи серверна СУБД

**Рекомендація для першої локальної версії: SQLite. Це ще не затверджений користувачем вибір.** Припущення: один backend на одному хості; DB writes централізовані в одному головному процесі, транзакції короткі. SQLite є SQL СУБД з дисковим файлом без окремого сервера; Python має стандартний `sqlite3`. У кожному connection потрібно явно вмикати й перевіряти FK enforcement (`PRAGMA foreign_keys=ON`).

Майбутній web frontend працює з backend API, а файл SQLite залишається локальним для backend. Сам факт вебінтерфейсу не вимагає серверної БД. При багатьох незалежних writers, кількох backend-хостах зі спільною БД або вимозі SQL stored procedures розглядати PostgreSQL/MySQL. Перенесення між СУБД не вважати безкоштовним: окремий storage API локалізує зміни, але DDL/SQL/міграції й перевірки потрібно адаптувати.

Офіційні джерела, перевірені 2026-11-23:

- [Застосування SQLite](https://www.sqlite.org/whentouse.html): локальне сховище, можливе використання для web backend, один одночасний writer, критерії client/server engine.
- [Python 3.13 sqlite3](https://docs.python.org/3.13/library/sqlite3.html): вбудований DB-API, без окремого server process; `Connection.create_function` реєструє функцію для connection.
- [SQLite foreign keys](https://www.sqlite.org/foreignkeys.html), [CREATE TRIGGER](https://www.sqlite.org/lang_createtrigger.html): реальні FK/triggers та правила їх застосування.
- [SQLite SQL syntax](https://www.sqlite.org/lang.html) і [SQLite forum: stored procedures](https://sqlite.org/forum/info/b7ea1c20fae4cc5d): у стандартного SQLite немає звичайних SQL stored procedures; application-defined function не є збереженою процедурою і потребує реєстрації у connection.

## Невирішений нюанс навчального завдання

Завдання перелічує таблиці, поля, тригери, функції, збережені процедури тощо. SQLite дозволяє тестувати таблиці/FK/checks/triggers і SQL functions, але не демонстрацію стандартного `CREATE PROCEDURE/CALL`. Чи вимагає викладач саме окремої збереженої процедури — не встановлено. Якщо так, для ПЗ рекомендовано MySQL/PostgreSQL; не підміняти процедуру Python-функцією й не оголошувати її протестованою. Якщо перевіряються відповідні компоненти обраної СУБД, SQLite може бути достатнім. З'ясувати це до залежної реалізації.

Кандидати змістовних DB checks: seed і JOIN через два FK; success/error rows; обов'язкові поля й числові межі; дубльований `(run_id, source_id)`; FK/cascade; trigger для узгодженості peak/parent metadata; atomic rollback result+peaks; історія після reopen. Окремо для MLT-2 перевірити паралельне виконання, bad-file continuation і аварію worker; ці перевірки не заміняються DB cases. Нічого з цього в цій планувальній задачі не запускалося.
