# Архітектурні рішення

Це рішення для наступного розвитку проєкту. Розділ `status.md` показує, які з них уже є в коді, а які ще треба реалізувати.

## D-01. Один top-level package на функціональний модуль

Кожен модуль MLT має власний Python-пакет `src/<module_name>/`: MLT-5 — `src/signal_proc/`; майбутні MLT-4/2/3/1 отримають окремі каталоги. Спільні DTO/пакети живуть у `src/audio_contracts/`. Це не дозволяє модулю читання WAV залежати від внутрішніх файлів DSP або навпаки.

**Наслідок:** імпорт MLT-5 — `from signal_proc import ...`; пакет distribution залишається `mlt-signal-processing`, що є окремим поняттям.

## D-02. Міжмодульний decoded input — `AudioPacket` v1

Один файл — один typed dataclass із `source_id`, optional `source_name`, `sample_rate_hz` і NumPy `samples[(frames, channels)]`. Моно канонізується до двох вимірів. Кількість каналів/кадрів/тривалість виводяться, не дублюються у вхідних полях. Integer PCM зберігає тип/масштаб до MLT-5; float зберігає свій масштаб.

**Чому:** модульний контракт незалежний від WAV-бібліотеки, перевіряється при створенні, підтримує mono/multichannel і pickle; float-нормалізація не губить семантику integer PCM.

## D-03. Помилка одного файла є даними одного завдання

MLT-4 повертає `AudioReadError`, якщо один файл не читається; він не створює неповний `AudioPacket`. MLT-2 пов’язує помилку з `source_id` і не зупиняє решту batch. Помилку обробки MLT-5 worker також має відокремити за джерелом; `process_signal` не повинен повертати валідно виглядаючий порожній результат замість винятку.

## D-04. У worker надсилається descriptor файлу, не великий decoded array

Рекомендований план MLT-2: parent ставить `FileJob(source_id, path, source_name)` у bounded task queue. У worker MLT-4 декодує файл, створює `AudioPacket` і без IPC-черги передає його до MLT-5 у тому самому процесі.

**Чому:** queue передає невеликий шлях замість серіалізації/копіювання всього WAV-масиву; межа MLT-4→MLT-5 однаково типізована. `FileJob` ще не створений у коді, бо MLT-2 відсутній.

Якщо парсер вже працює у parent, допустимий простий pickle-вариант для першої версії; його накладні витрати треба виміряти. Shared memory — лише після benchmark, разом із протоколом власності та звільнення сегментів.

## D-05. Результати корелюються через `source_id`

Порядок завершення worker-ів може відрізнятися від порядку вибору файлів. Не покладайся на позицію в списку; UI та aggregator зіставляють `SignalPacket`/помилки за стабільним `source_id`. `source_name` потрібний для показу, але може дублюватися.

## D-06. Performance порівнюється контрольовано

Послідовний baseline і worker pool отримують той самий набір файлів, ті самі параметри та середовище; окремо міряється повний час і, за потреби, parsing/DSP. Не закладати обов’язковий speedup: короткі файли можуть програти через запуск процесів/IPC. Конкретний поріг поки не погоджений.

## D-07. Код і KB мають окремі історії в тому самому remote

`main` містить код і звичайну документацію проєкту. `kb-only` — orphan-branch без спільного предка з `main`, у дереві лише KB-документи. Один GitHub remote: `https://github.com/VladislavCalculus/Muliprosessing-Analisis.git`. Кореневий `.gitignore` ігнорує локальний worktree `knowledge-base/`; push KB виконується лише в `origin/kb-only`.

## D-08. Джерела контексту мають різну вагу

1. Поточний код — факт про реалізовану поведінку.
2. Live Jira — джерело поточних issue fields/status/assignee/sprint на час конкретного запиту; записуй дату спостереження. Project identity/API доступ підтверджено, але повний issue state ще не синхронізовано (див. `jira.md`).
3. README/pyproject — публічний контракт і середовище, звірені з кодом.
4. Користувацькі звіти та Jira-знімки — вимоги й історичне планування; `To Do`, очікуваний результат або bug report не доводять виконання/дефект.
5. Висновки з планів позначаються як рекомендований дизайн, доки їх не реалізовано або не підтверджено Jira/виміром.

## D-09. Агент самостійно синхронізує спільну KB

Кожен агент спершу fetch-ить `origin/kb-only`, читає актуальну KB, перед комітом повторно синхронізує remote, розв’язує Markdown-конфлікти за доказами, а потім пушить без force. У фізично спільному checkout з незакоміченою паралельною роботою використовуй ізольований detached worktree. Не запитуй розробника про конфлікти змісту; невирішну фактичну суперечність документуй як непідтверджену з джерелами/датами. Детальний алгоритм — [`collaboration.md`](collaboration.md).

## D-10. Вибрані Jira-задачі проходять role-based цикл із доказовим Done gate

Для MLT задач/спринтів, які користувач прямо вказав як роботу, агент спершу читає live Jira і вибудовує залежності, потім виконує кодову зміну, незалежний review і лише після цього змінює статус Jira. Ролі мають чіткі межі: fetcher — read-only; implementer — код без Jira writes; reviewer — read-only; bug reporter — створення доказового Bug після duplicate search; updater — transition/comment тільки для вибраних keys.

**Наслідки:** кожний issue закривається окремо; не робляться bulk transitions, незавершені sprint задачі не позначаються Done, а підтверджені позаскопові дефекти отримують Bug issue. Перед transition треба отримати доступні Jira transitions, після — перечитати status і Resolution. Jira status і Resolution окремі; значення Resolution має походити з workflow/transition, а не здогадки агента. Локальна реалізація Codex roles і MCP write filters лишається в ignored `.codex/`; KB зберігає переносимі правила, не credentials чи host-specific config.
